Critical correction

Why the direct-launch path fails

The spec's plan

SCREEN_OFF received → startActivity(lockscreen) straight from the receiver.

On Android 12+ this is a Background Activity Launch. A running foreground service is not on the exemption list. The call is silently dropped — no crash, no screen.

The working plan

SCREEN_OFF received → post a full-screen-intent notification whose PendingIntent opens the Activity.

FSI routes through system notification infra, which has its own launch privilege. Fallback: draw a TYPE_APPLICATION_OVERLAY window.

Android 15 also narrowed the SYSTEM_ALERT_WINDOW launch exemption: holding the permission isn't enough — an overlay must be visibly on screen at launch time. FSI sidesteps this.

This is the single most important slide. If we build it the way the spec literally says, it will work in the emulator sometimes and fail on real devices/newer OS versions intermittently — the worst kind of bug. The FSI notification is how Glimpse and similar apps actually do it. Source: developer.android.com background-starts + Android 14/15 behavior-changes.

Key engineering detail: settings screens return no result. Use a lifecycle ON_RESUME observer to re-read each permission's state every time the user comes back, and reactively update the checklist. Make step 5 (battery) clearly optional/skippable — it's a per-OEM nag and shouldn't block first run.

Phase 2

Media engine — listener as the heart

Connect

onListenerConnected() → get MediaSessionManager, register active-sessions listener, register SCREEN_OFF receiver here.

Observe

Attach MediaController.Callback: onMetadataChanged, onPlaybackStateChanged. Push into the repo StateFlow.

Expose

NowPlaying(title, artist, art, isPlaying, positionMs, durationMs) — an @Immutable data class.

Switch

addOnActiveSessionsChangedListener handles app switches (Spotify → Apple Music) — rebind the callback to the new top controller.

getActiveSessions() needs your listener's ComponentName as the permission token — pass ComponentName(ctx, MediaListener::class.java).

Gotcha: getActiveSessions throws SecurityException if notification access isn't granted — guard it. Album art comes from MediaMetadata.METADATA_KEY_ALBUM_ART / ART as a Bitmap, no extra permission. Rebind on session change so the controls always point at whatever is actually playing.

Phase 3

The screen-off trigger

Register dynamically

ACTION_SCREEN_OFF is a protected broadcast — manifest receivers are ignored. Register in code (in the listener), with RECEIVER_NOT_EXPORTED.

Gate on playback

On SCREEN_OFF: if repo.value.isPlaying → fire FSI notification. Else do nothing.

Launch order of preference: 1) FSI notification (canUseFullScreenIntent) → 2) overlay window (canDrawOverlays) → 3) plain high-priority notification (last resort, user taps to open).

The three-tier fallback is what makes this robust across OEMs and OS versions. We pick the best available launch channel at runtime based on which permissions the user actually granted. Log which tier fired — invaluable for field debugging.

Phase 4

The Compose lockscreen

Flags first

In onCreate: setShowWhenLocked(true), setTurnScreenOn(true), KEEP_SCREEN_ON. Declare TURN_SCREEN_ON in manifest.

Ticking progress

LaunchedEffect(isPlaying) loops delay(1000) incrementing position locally; snaps to real position on each state change.

Swipe to unlock

detectVerticalDragGestures; past threshold → finish() reveals the real secure keyguard (PIN/pattern).

Two themes via a CompositionLocal switch: Minimalist Dark (solid bg) and Glassmorphism (album art as blurred edge-to-edge backdrop using Modifier.blur + scrim).

setShowWhenLocked draws OVER the keyguard — it does NOT bypass PIN. finish() simply removes our activity and the secure keyguard is still there underneath, which is exactly the behavior we want. Follow the compose-performance skill: @Immutable state, hoist the ticker, derive progress with derivedStateOf to avoid recomposing the whole screen every second.
